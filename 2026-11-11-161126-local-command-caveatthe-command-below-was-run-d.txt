  Answers are from the docs at https://code.claude.com/docs/en/sandboxing.md and
  https://code.claude.com/docs/en/hooks.md. The pages I read did not cover the
  settings reference, so the `agent` settings key is unverified.

  1. Yes, `sandbox.excludedCommands` exists. Entries use the same syntax as a
  `Bash(...)` permission rule: no wildcard means exact match, and `docker *`
  matches with or without arguments. Every command in a compound call must
  match. Matching is on the call text, so a script that calls `docker`
  internally, or `/usr/local/bin/docker`, does not match. Excluded commands run
  fully outside the sandbox, with no filesystem restriction and no proxy, so
  they can read `~/.config/gh`. Doc: sandboxing.md, "Run commands outside the
  sandbox with excludedCommands".
  2. Only the retry is disabled. The doc says that with
  `allowUnsandboxedCommands` off, "Claude Code ignores the
  `dangerouslyDisableSandbox` parameter... commands Claude runs are then
  sandboxed unless they match an `excludedCommands` entry." Doc: sandboxing.md,
  "The unsandboxed retry escape hatch".
  3. Excluded commands still go through the permission flow. Read-only commands
  and commands your allow rules cover run without a prompt, and other excluded
  commands get the classifier in auto mode. `autoAllowBashIfSandboxed` only
  affects sandboxed commands. The docs do not say whether PreToolUse hooks fire
  for excluded commands or how they are ordered relative to permission rules.
  Hooks can deny, and silence does not approve. Doc: sandboxing.md; hooks.md,
  "PreToolUse" walkthrough.
  4. Hooks run outside the sandbox: "command hooks... run with your full
  access." So a hook can write `.claude/hooks/` regardless of Bash write denies.
  Doc: sandboxing.md, "What runs outside the sandbox".
  5. `agent_type` is present "when the session uses `--agent` or the hook fires
  inside a subagent." `agent_id` is "the subagent or in-process teammate the
  hook fires in." The settings key `"agent": "lead"` is not documented in the
  pages I read. Doc: hooks.md, "Common input fields".
  6. Yes: `sandbox.filesystem.allowWrite` and `denyWrite`, with reads via
  `denyRead` and `allowRead`. The Gradle/`~/.gradle` case is not documented in
  the pages I read. Doc: sandboxing.md, filesystem section;
  settings-reference.md#sandbox-filesystem-allowwrite.

  Implications for the token goal: subagents use the same sandbox config
  (sandboxing.md, "Scope"), and excludedCommands matches command text, not
  caller. So an `excludedCommands` entry for `gh *` lets a subagent's `gh` read
  the token too. A PreToolUse hook that checks `agent_id` and denies Bash from
  subagents is the documented mechanism, but its ordering against exclusions is
  unverified.

  - **Attached short flags:** `gh api repos/o/r/x -XDELETE`, `-XPATCH` and
  `-fa=b`. `gh api -X=POST` is denied, but `-XPOST` is not.
  - **GraphQL payloads that hide the mutation:** `gh api graphql -F
  query=@q.graphql` and `gh api graphql --input q.json`.
  - **Missing subcommands:** `gh workflow run`, `gh release upload`, `gh repo
  fork`, `gh repo sync`, `gh project item-create`, `gh pr update-branch`, `gh
  label clone`, `gh cache delete`, `gh codespace create` and `gh ssh-key add`.

  Suggested fix: invert to a read-only allowlist for subagents.

  ### 3. `git push` guard bypasses
  - **Globs reach the protected branches.** The destination `*` is not in the
  protected set, so `git push origin 'refs/heads/*:refs/heads/*'`, `git push
  origin feature/*:refs/heads/*` and an unquoted `refs/heads/*:refs/heads/*` are
  allowed. The lead's glob push can update `dev`, `staging` and `main`. Deny
  any `*` in a refspec.
  - **Quoted or indirect branch names are allowed:**
    - `git push origin "dev"` and `git push origin 'main'`. The quotes are not
  stripped.
    - `B=dev; git push origin $B` and `git push -u origin $(echo dev)`.
    - `bash -c "git push origin dev"`, `sh -c '...'` and `(git push origin
  dev)`. The leading `(` defeats the `git` token match.
    - `git -C "my dir" push origin dev`.
    - `HEAD:heads/dev`. Git resolves an unqualified `heads/dev` to
  `refs/heads/dev`.
    - Only the sandbox and the permission deny rules cover these. The permission
  deny rules match exact strings only.
  - **Abbreviated long flags** are allowed because only exact flag names are
  checked:
    - `--al`, `--mir`, `--prun` for `--all`, `--mirror` and `--prune`.
    - `--del` for `--delete`.
  - **Combined short flags for deletes:** `git push -ud origin feature/x` as the
  implementer is allowed. This breaks "only the lead deletes remote branches".
  The `-d` check is an exact match.
  - **Upstream mapping:** a bare `git push` or `git push origin` uses
  `currentBranch()`. Git can instead push to a different upstream under
  `push.default=upstream`.
  - **Tag push:** `git push origin refs/tags/v1` by the lead is allowed. This
  looks acceptable.
  - **`-C` working directory:** `currentBranch()` uses the hook's `cwd`, not `-C
  <dir>`.

  ### 4. False denials that block normal lead work
  - **Commit messages:** `git commit -m "Block curl to api.github.com"` is
  denied by the curl rule. The word `curl`, a space and a GitHub host in a
  quoted string is enough.
  - **Commit messages and PR bodies naming the token command:** `git commit -m
  "mention gh auth token"` is denied, and so is `gh pr create --body "uses gh
  auth token docs"`.
  - **PR bodies with a semicolon:** `gh pr create --body "use curl
  https://github.com/x" ...` is denied. So is `gh pr create --body "a; git push
  origin dev; b"`, because splitting on `;` and `|` ignores quotes.
  - **Likely impact:** this PR's own description and DEVELOPMENT.md-style text
  will hit these. The lead must use `--body-file` or `-F`.
  - **Pacing:** a quoted `;` inside a commit message can create a fake push
  segment that counts toward pacing.
  - **Related gap:** `python`, `node`, `nc`, `curl https://API.GITHUB.COM` (the
  host check is case-sensitive) and `xh` are not caught. Sandboxed commands
  cannot read the token, so this is minor.

  ### 5. DEVELOPMENT.md and CLAUDE.md overstate the guarantees
  - "No printing the token" and "Nobody pushes dev/staging/main, force-pushes or
  pushes --all/--mirror" read as hard guarantees. See findings 1 to 3.
  - "Ordinary commands can't see the token" is true for ordinary commands. But
  `gh *` is excluded, so the hook is the only barrier there.
  - The docs do not tell the lead to use `--body-file` because of the false
  denials in finding 4.
  - DEVELOPMENT.md §3 says a compound command runs outside the sandbox only if
  every part matches. I could not verify this, because I can't run `gh`
  unsandboxed.
  - `excludedCommands` `git push *` does not cover `git -C . push` or `env git
  push`. Those run sandboxed and probably fail on credentials. That is a safe
  failure, but it is not documented.
  - The hook source comment says it "Fails open only if the hook input itself
  can't be read". That is accurate.
  - The pacing and fail-closed behaviour in the docs match the code.

  ### 6. Positive findings from the settings
  - **Write protection:** `.git/hooks`, `.git/config`, `.claude/hooks` and
  `.claude/settings.json` are not writable from the sandbox. This blocks
  planting a pre-push hook or a credential helper to run unsandboxed.
  - **Token and secrets:**
    - No `GH_TOKEN` is in the sandbox environment.
    - `.claude/hooks/.state/` is in `.gitignore`.
    - No secrets or Firebase config are committed.
    - Nothing is deleted.

  **1. A wrapper in front of `gh` or `git push` bypasses the whole hook. This is
  verified for real, not just in the harness.**
  - **What I ran as the verifier subagent.** The plain command `gh auth status`
  returned "Logged in ... Token: gho_****", so it ran unsandboxed. Each of these
  also returned "Logged in", so each also ran unsandboxed:
    - `env gh auth status`
    - `timeout 5 gh auth status` and `timeout -s KILL 5 gh auth status`
    - `nohup gh auth status`
    - `nice gh auth status`
    - `time gh auth status`
    - `stdbuf -o0 gh auth status`
  - **Why.** Claude Code strips those wrappers when deciding whether a command
  matches `gh *` and `git push *`. The hook only looks at the first word, so it
  sees `env` or `timeout` and exits. Harness results:
    - allow [implementer] `timeout 5 gh alias set x '!git push origin dev'`
    - allow [implementer] `env gh auth git-credential get`, which prints the
  token
    - allow [implementer] `nohup gh api repos/o/r/x -XDELETE`
    - allow [lead] `env git push --force origin dev`
    - allow [lead] `timeout 5 git push origin dev`
  - **What stays sandboxed.** `FOO=1 gh ...`, `/usr/bin/gh`, `command gh`,
  `\gh`, `"gh"`, `setsid`, `ionice` and anything in a pipe or `&&` returned "not
  logged in".
  - **Fix.** Before judging a segment, strip leading `NAME=value` words and the
  wrappers `env`, `timeout` (with its option and duration arguments), `nohup`,
  `nice`, `time` and `stdbuf`. Then apply the gh and git-push rules to the
  result. More robust: deny any segment that contains the exact word `gh`, or
  `git` followed by `push`, anywhere in the segment, unless it is a plain `gh`
  or `git push` command in first position.

  **2. Subagents can still make `gh api` writes with bundled short flags.** The
  hook only recognises `-X` and `-f` when they stand alone or are attached
  directly, but pflag lets short flags bundle.
  - allow [implementer] `gh api user -iXPOST`
  - allow [implementer] `gh api user -pXPOST`
  - allow [implementer] `gh api -iXDELETE repos/o/r/x`
  - allow [implementer] `gh api -if a=b repos/o/r/x`
  - allow [implementer] `gh api -ifa=b repos/o/r/x`
  - allow [implementer] `gh api -XGET user` (harmless, but shows the parser
  misses attached forms)

  **Fix:** deny any `gh api` argument that matches `^-[A-Za-z]{2,}`. The
  `endpoint = first non-dash token` logic also treats the value of `-H` or
  `--hostname` as the endpoint. Parse the flags that take a value properly.

  **3. The lead can publish the token or write outside the intended repo.** This
  matters for prompt injection against the lead, since lead `gh` writes are
  otherwise trusted.
  - **File arguments are unchecked.** `gh issue comment 1 -F
  /home/walde/.config/gh/hosts.yml` is allowed and would post the token into a
  public issue. So are `gh pr create --body-file /etc/passwd --title t` and `gh
  api repos/EthanScottWalden/ColPool/issues/1/comments -F
  body=@/home/walde/.config/gh/hosts.yml`. Only `~` is blocked, because the
  tokenizer flags it, not a policy check. **Fix:** allow `--body-file`, `-F
  file` and `@file` only under the repo or `$TMPDIR` or the scratchpad.
  - **Lead `gh api` non-GET calls are unrestricted.**
    - Allowed: `gh api -X DELETE repos/o/r/git/refs/heads/dev`, `gh api
  repos/o/r/branches/dev/protection -X DELETE` and `gh api repos/o/r/rulesets -X
  PUT -f x=y`.
    - Allowed: any GraphQL mutation, for example `deleteRepository` and
  `updateRepository`.
    - These contradict the "nothing is deleted" rule and the ruleset protection
  for `dev`, `staging` and `main`.
    - **Fix:** limit lead `gh api` writes to an allowlist of endpoints and
  mutations, for example `repos/EthanScottWalden/ColPool/issues|pulls/...` and
  `updateIssue`, `updateProjectV2ItemFieldValue` and `addProjectV2ItemById`.
  - **The repo restriction is easy to dodge with a URL.** allow [lead] `gh pr
  merge https://github.com/other/repo/pull/1` passes, so a PR URL targets
  another repo. Also check any URL or `owner/repo` argument.
  - **`gh pr merge 1 --admin` is allowed.**

  **4. Smaller points.**
  - `gh pr view 1 --web` and `gh project view 1 --web` are allowed and open a
  browser unsandboxed. This is low risk.
  - `git push origin Dev` is allowed. It is harmless because GitHub branch names
  are case-sensitive.
  - `git push origin feature/.x` and `feature//x` pass the hook and are rejected
  by git.
  - `git push origin HEAD` is denied for the lead. It is only an inconvenience;
  the docs should say so.
