## Problems (evidence, cost, cause)
1. **Parallel worktree implementers again (Mon 23 Nov).**
   - Evidence: the #20 and #21 implementers ran in worktrees at the same time. From the worktree, the hook rejected #21's GitHub script calls (`push`, `issue-view`). #21's WIP commit `e689df2` exists only in the local repo, with a `prompt.md` handoff note. #20 stopped with uncommitted changes in its worktree.
   - Cause: the lead took the owner's approval of parallel phases as permission for parallel implementers, which goes against last week's rule. The owner didn't restate the rule. When told to stop only #21, the lead let #20 stop as well and didn't restart it until the owner asked.
   - Fix: back to one implementer in the main checkout.
2. **"One staging PR per Issue" wasn't possible as offered (Mon 23 – Tue 24 Nov).**
   - Evidence: the owner chose one dev → staging PR per Issue on Mon 23 Nov. The lead opened no staging PR after #20 merged (it deferred the docs pass). The first, PR #145, opened after #20, #23, #28 and #30 had merged, and grew to seven Issues. The owner asked on Tue 24 Nov: "didn't I say to have one PR for each issue?"
   - Cause: a dev → staging PR always contains everything in dev that isn't in staging yet. One PR per Issue works only if each promotion merges before the next Issue lands in dev. The lead offered the option without saying so, then didn't follow it either.
   - Fix: owner decision 2026-11-24, one rolling staging PR with a section and a review checkbox per Issue. Lesson: when offering a process option, state what it needs from the owner (here, reviewing every 30–45 minutes).
3. **A blocking question idled all work for ~2 h 50 min (Mon 23 Nov, ~10:47 – 13:38).**
   - Evidence: the lead asked the Mon–Fri weekday question for #24 in the choice dialog, which pauses the lead until answered. #35 sat reviewed but unmerged, and #24 didn't start.
   - Cause: a safe default existed (Mon–Fri, as in the prototype), and the lead asked a blocking question instead of applying it provisionally.
   - Fix: when there's a reasonable default, apply it provisionally and ask in a normal message.
4. **No progress overnight (Mon 23 – Tue 24 Nov).** The lead said it would keep working, but its turn ended. CI finishing doesn't wake the session, so #24's green PR waited until the owner's next message.
5. **Lead process slips (Wed 25 Nov).**
   - A branch switch to a stale local `dev` half-failed, because `.claude/` is read-only in the sandbox; the owner ran `git checkout -f -B feature/143-stop-limit-10 origin/dev`. Lesson: branch from `origin/dev` directly, never check out local `dev` (now in `DEVELOPMENT.md` §3 "Branching in the sandbox").
   - The lead told the owner that closing the staging Issues would open Phase 4. Wrong: the phase rule needs all Phase 2/3 Issues Done. Corrected.
   - The lead offered a #52 "straight-line" label note without checking that the cards already say it.
   - The lead didn't log clock times at checkpoints; times below are rebuilt from commits.
6. **A device check found what automated checks didn't.** #154 passed QA and review but the owner's emulator check found the doubled header inset, the stale match %, and the missing Profile button. Cost: about 42 min of rework (#162).
7. **The deploy runbook missed a fresh project's setup (Fri 27 Nov).**
   - Evidence: the owner hit, in order: the AIDev account had no role on `colpool`; no Firestore database existed (step 4 returned 404); Cloud Build failed for all four functions (default compute service account lacked `roles/cloudbuild.builds.builder`); the Cloud Run services had no invoker, so the app got `PERMISSION_DENIED`; Authentication was off (`CONFIGURATION_NOT_FOUND`); `signUp` failed with `auth/insufficient-permission` (service account lacked `roles/firebaseauth.admin` and `roles/datastore.user`); the Web API key wasn't shown in Project settings. The runbook also said "3 calls" for a check that makes 2, ran steps out of number order (12 before 10) without saying why, didn't warn that `read -rs` waits silently, and left out the Android Studio route. About seven round trips to the lead.
   - Cause: the runbook was rehearsed only against the emulators, which hide all of this setup, and the lead wrote the fresh-project parts from memory without checking current Google defaults (new projects no longer give the default service account broad roles).
   - Fix: rewrite the runbook in run order with every step above (open follow-up). Lesson: before a first-time real-environment step, check fresh-project defaults in the official docs and list what the emulator hides; verify the owner's account access first.
8. **Pattern across the week (owner and lead review, Fri 27 Nov).** "Passes in the emulator or tests" or "seems right" was treated as done: the Phase 4 claim and the #52 note (Problem 5), five device-check defects (Problem 6), the runbook (Problem 7), and two more Create Series defects the owner found on Fri 27 Nov.
